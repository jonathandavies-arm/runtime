# Vector helper performance investigation

Investigation tools and recorded results for dotnet/runtime PR #132117. This branch is based on `05cea1dca36` (`Restrict Vector helper imports to Arm64`); these files are separate from the implementation change.

The custom harness measures execution time for 744 cases:

- Vector64/128 helpers with byte, short, int, long, float and double elements: Count, IndexOf, LastIndexOf, Any, All, None, and their WhereAllBitsSet forms.
- Absent, first, last and all-lane matches, plus floating-point NaNs.
- Span byte/short/int IndexOf, LastIndexOf and Count at lengths 16, 64, 256 and 4096.

`Program.cs` is generated by `generate.py`; `Bench.csproj` compiles only that file. Each case checks its result before timing, then measures batches of 4096 operations after warmup. Timings include loop and array access overhead. Methods are isolated with NoInlining. This is a custom Stopwatch harness, not BenchmarkDotNet, and does not measure compilation time or establish application-level improvements.

## Recorded results

All measurements were taken on a Cortex-X925, CPU 5, with tiering and ReadyToRun disabled. Only the JIT changes between variants; runtime and CoreLib remain identical.

The latest run retains representative Count improvements of 22–28%, IndexOf improvements of 4–10%, and LastIndexOf improvements of 11–12%. The standard suite classified 23 cases as unchanged and one as slower: Span<int>.LastIndexOfValue at length 4, 1.895 to 2.016 ns (+6.4%). An initial custom byte-span slowdown did not reproduce in longer checks. Boolean helpers showed no clear gain.

Reports in `results/` are historical snapshots. Paths and command names inside them refer to the original workspace; `commands/` subdirectories preserve selected exact scripts for provenance. Use the configurable scripts here for new runs. No runtime binaries, build outputs, downloaded MCH collections, or large assembly dumps are committed. Code-size comparisons cover successfully replayed contexts; the reports disclose missing records and collection limitations.

## Run the custom harness

Requires Linux ARM64, Python 3, taskset, a .NET 12 SDK, matching baseline/candidate JITs and a compatible runnable Core_Root. The default SDK is the repository's `.dotnet/dotnet`. Recorded runs used SDK `12.0.100-alpha.1.26557.102`.

From the runtime repository root:

```bash
python3 eng/performance/vector-helper-investigation/run.py \
  --core-root /path/to/matching/Core_Root \
  --baseline-jit /path/to/main/libclrjit.so \
  --candidate-jit artifacts/bin/coreclr/linux.arm64.Release/libclrjit.so \
  --output artifacts/vector-helper-perf/current \
  --cpu 5

python3 eng/performance/vector-helper-investigation/analyze.py \
  artifacts/vector-helper-perf/current
```

The runtime directory must contain corerun, libcoreclr.so and System.Private.CoreLib.dll. If framework assemblies are separate, add `--framework-dir /path/to/matching/framework`. Framework files are copied first; Core_Root files take precedence. The baseline and candidate JITs must match the runtime's JIT/EE interface. An arbitrary installed runtime may be incompatible. The runner stages two complete directories and changes only libclrjit.so; inherited CORE_ROOT is replaced for each child process.

Use a fresh output directory. Defaults are five alternating process passes and 10 ms per case/pass. `run.json` records paths, parameters and binary hashes. `base-*.csv` / `current-*.csv` contain samples. The analyzer writes `comparison.csv` and `SCREENING.md`.

To confirm selected cases, specify exact names separated by `|` and increase duration:

```bash
python3 eng/performance/vector-helper-investigation/run.py \
  --core-root /path/to/matching/Core_Root \
  --baseline-jit /path/to/main/libclrjit.so \
  --candidate-jit artifacts/bin/coreclr/linux.arm64.Release/libclrjit.so \
  --output artifacts/vector-helper-perf/confirmation \
  --filter 'V128_int_Count_last|Span_byte_64_LastIndexOf_first' \
  --duration-ms 250 --passes 5 --cpu 5
```

Add `--disasm` in a separate run to collect diffable JIT assembly; do not use timings from disassembly runs as performance evidence. The screening rule (>5% median change and non-overlapping observed ranges) is not a formal significance or equivalence test. Confirm flags with longer runs and disassembly; small differences can vary with process/code layout.

To rebuild the current JIT with the direct native build entry point, explicitly enable JIT compilation:

```bash
src/coreclr/build-runtime.sh -arm64 -release -ninja -component jit \
  -cmakeargs '-DFEATURE_DYNAMIC_CODE_COMPILED=1'
```

The recorded main baseline is `00236714c28b30ae2522b348d11315e509cf4425`; original PR head is `e8ea6fced00eb152330971ff3817692e1ca07e1e`. Build a matching runtime/CoreLib separately or use a compatible complete Core_Root. Generating the harness again is optional: `python3 eng/performance/vector-helper-investigation/generate.py`.

## Run the existing dotnet/performance selection

The standard suite source was unchanged, at performance commit `262db8039904ac2836fa9640f6b4d351f94118fc`. That suite has no direct benchmarks for the new value-count/search helpers. Its vector CountBenchmark reads the lane-count property. The selected span benchmarks search for a midpoint match, unlike some custom inputs.

Build the suite using a .NET 12 SDK:

```bash
.dotnet/dotnet build /path/to/performance/src/benchmarks/micro/MicroBenchmarks.csproj \
  -c Release -f net12.0 -p:TreatWarningsAsErrors=false
```

The preview SDK used for the investigation required the warnings override for NuGet warnings. Then reuse the two runtime directories staged by run.py:

```bash
python3 eng/performance/vector-helper-investigation/run_bdn.py \
  --performance-repo /path/to/performance \
  --runtimes artifacts/vector-helper-perf/current \
  --output artifacts/vector-helper-perf/bdn-current \
  --launches 3 --cpu 5
```

This runs IndexOfValue and LastIndexOfValue for byte/char/int spans at lengths 4, 33, 512 and 3000: 24 cases, each on two JITs. Settings are five warmups, 15 measured iterations, 100 ms target duration and a 5% statistical comparison threshold. The command is saved to command.json; BDN produces its own reports. Three-launch runs took about eight minutes on the recorded machine. Avoid other CPU-intensive work while timing.
